# Lab 2 Sprint Engineering Specification

## 1. Sprint Goal
Deliver a responsive, user-friendly Requester-facing MVP for TokTickIT that enables simulated Requesters to create IT support tickets with permitted attachments, track their submitted tickets via search, filter, sort, and pagination, inspect ticket details, and manage attachments under strict ownership protection and soft-removal rules using the Zen Green Design System.

## 2. Stakeholder Request Interpretation
The IT department requires a self-service web portal for company employees (Requesters) to report IT issues (Account/Access, Hardware, Software, Network). Requesters must be able to submit tickets with descriptions, system selections, priority ratings, and attachments. Since enterprise authentication will arrive in Sprint 3, Sprint 2 requires a temporary "Development Requester Selector" to simulate multi-user environments so testers can verify that each Requester sees and manages only their own tickets and attachments.

## 3. Scope

### Included
1. **Development Requester Context:** Selection screen allowing switching between active seeded requesters; application shell reflecting current requester identity.
2. **Create Ticket Workflow:** Form with classification, priority, description, system-generated fields (Ticket Number, Date), and client/server validation.
3. **My Tickets Workflow:** Paginated list showing only tickets owned by the current requester, with search, filtering (Category, Priority, Status), and sorting.
4. **Requester Ticket Detail Workflow:** Read-only view of owned ticket details and status.
5. **Attachment Lifecycle:** Uploading permitted files (JPG, PNG, WEBP, PDF up to 5MB, max 5 active), downloading active files, and soft-removing files with mandatory audit reasons.
6. **Zen Green Design System:** Cohesive responsive layout (Desktop, Tablet, Mobile) adhering to required color tokens, states, and accessibility guidelines.

### Explicitly Excluded
1. Real authentication & security (passwords, JWT, sessions, RBAC, login/logout).
2. IT Staff workflows (agent queue, claiming tickets, triage, updating IT priority, resolving/closing tickets).
3. Ticket status progression beyond initial `New` state.
4. Ticket collaboration tools (Public Comments, Internal Notes, Actions Taken).
5. Administrator management of users, roles, and master catalog data.

## 4. Functional Requirements
- **FR-01 (Requester Selection):** The system must allow users to choose an active Development Requester from a dropdown populated from the database.
- **FR-02 (Requester Identity Persistence):** The chosen requester identity must persist across page navigation and be visibly displayed in the application header.
- **FR-03 (Requester Switching):** Users must be able to change the active requester at any time, which must immediately reload and isolate data to the new requester.
- **FR-04 (Ticket Creation):** Requesters must be able to submit a ticket by choosing a Category, a Related System, a Requested Priority, entering a Ticket Summary, and a detailed Description.
- **FR-05 (System Defaults & Generation):** Upon creation, the backend must generate a unique, formatted Ticket Number (e.g., `TKT-YYYY-NNNNNN`), set the Ticket Date to current timestamp, and assign initial status `New`.
- **FR-06 (Form Resilience):** If backend submission fails, the form must preserve all user-entered inputs without data loss.
- **FR-07 (My Tickets Retrieval):** The system must display a list of tickets belonging strictly to the selected requester.
- **FR-08 (Search & Filtering):** Requesters must be able to filter their tickets by Category, Priority, and Status, and search by ticket number or summary keyword.
- **FR-09 (Sorting & Pagination):** The ticket list must support sorting by date and priority, and display results across paginated pages with configurable or sensible page sizes.
- **FR-10 (Ticket Detail View):** Requesters must be able to view complete details of an owned ticket in read-only mode.
- **FR-11 (Attachment Upload):** Requesters must be able to upload valid attachments (JPG, JPEG, PNG, WEBP, PDF; ≤5MB) during creation or to an existing owned ticket (up to 5 active attachments).
- **FR-12 (Attachment Soft Removal):** Requesters must be able to soft-remove an active attachment by providing a non-empty removal reason.
- **FR-13 (Download Protection):** Active attachments must be downloadable by their owner; soft-removed attachments must show metadata only and block downloading.
- **FR-14 (Cross-Requester Protection):** Any attempt to view, list, download, or alter tickets or attachments belonging to another requester must be rejected (HTTP 403/404).

## 5. Business Rules (BR)
- **BR-01 (Official Ticket Number):** Every ticket must receive an official, globally unique Ticket Number generated by the backend with the format `TKT-YYYY-XXXXXX` (e.g., `TKT-2026-000101`).
- **BR-02 (Initial Status):** All newly created tickets must be assigned the initial status `New`.
- **BR-03 (Dev Requester Context):** The Development Requester Selector is strictly a testing harness and does not constitute secure authentication.
- **BR-04 (Inactive Requesters):** Requesters flagged as `active: false` must never appear in the Development Requester selection dropdown.
- **BR-05 (Strict Ownership Isolation):** A Requester may only view and query tickets where `requesterId` matches their currently active development identity. Direct URL access to another requester's ticket must return 404 or 403.
- **BR-06 (Attachment Limits & Formats):**
  - Permitted MIME types: `image/jpeg`, `image/png`, `image/webp`, `application/pdf`.
  - Maximum size per file: exactly 5 MB (5,242,880 bytes).
  - Maximum active attachments per ticket: exactly 5.
- **BR-07 (Soft-Removal Rule):** When an attachment is removed:
  - The record is marked `active: false`, with `removedAt` timestamp and non-empty `removalReason`.
  - The physical file is retained or preserved for audit purposes.
  - The attachment remains visible in the UI metadata list labeled as "Removed" with the reason displayed, but download/preview actions are permanently disabled.
- **BR-08 (Field Length & Validation Constraints):**
  - `Summary`: Required, trimmed, minimum 5 characters, maximum 120 characters.
  - `Description`: Required, trimmed, minimum 10 characters, maximum 2,000 characters.
  - `Category`: Required; must reference an existing active category ID.
  - `Related System`: Required; must reference an existing active related system ID.
  - `Requested Priority`: Required; one of `Low`, `Medium`, `High`, `Critical`.

## 6. UI Specification Summary
The UI adheres strictly to the **Zen Green Design System**:
- **Color Tokens:**
  - Primary Green: `#006B3C` (Header, primary buttons, brand accents)
  - Secondary Green: `#0B7A46` (Active tabs, focus rings, links, hover)
  - Pale Green: `#EAF6EF` (Selected cards, success callouts, section highlights)
  - Page Background: `#F5F7F6`
  - Surface/Card: `#FFFFFF` with border `#D0E0D8` and subtle elevation shadow
  - Text: Dark Charcoal-Green `#1B3A2A`
  - Error: Dark Red `#B02A37`
  - Warning: Amber `#B58105`
- **Responsive Viewports:**
  - **Desktop (≥992px):** Two-column/multi-column forms, full data table with sorting headers.
  - **Tablet (768–991px):** Two-column adaptive grid, compact table.
  - **Mobile (<768px):** Single-column stacked layout, responsive ticket cards, touch targets ≥44px, zero horizontal overflow.
- **Component Rules:**
  - Red asterisk (`*`) for required fields.
  - Inline error messages rendered directly beneath failing controls.
  - Submit button shows spinner and enters disabled state during network requests.

## 7. Data Changes (Prisma & PostgreSQL)

```prisma
model Requester {
  id        Int       @id @default(autoincrement())
  name      String
  email     String    @unique
  active    Boolean   @default(true)
  createdAt DateTime  @default(now())
  tickets   Ticket[]
}

model RelatedSystem {
  id        Int       @id @default(autoincrement())
  name      String    @unique
  active    Boolean   @default(true)
  createdAt DateTime  @default(now())
  tickets   Ticket[]
}

model Category {
  id        Int       @id @default(autoincrement())
  name      String    @unique
  createdAt DateTime  @default(now())
  tickets   Ticket[]
}

model Ticket {
  id              Int           @id @default(autoincrement())
  ticketNumber    String        @unique
  ticketDate      DateTime      @default(now())
  summary         String
  description     String
  priority        String        // Low | Medium | High | Critical
  status          String        @default("New")
  requesterId     Int
  categoryId      Int
  relatedSystemId Int
  createdAt       DateTime      @default(now())
  updatedAt       DateTime      @updatedAt

  requester     Requester     @relation(fields: [requesterId], references: [id])
  category      Category      @relation(fields: [categoryId], references: [id])
  relatedSystem RelatedSystem @relation(fields: [relatedSystemId], references: [id])
  attachments   Attachment[]

  @@index([requesterId])
  @@index([status])
  @@index([categoryId])
}

model Attachment {
  id            Int       @id @default(autoincrement())
  filename      String
  originalName  String
  mimeType      String
  sizeBytes     Int
  active        Boolean   @default(true)
  removalReason String?
  removedAt     DateTime?
  ticketId      Int
  createdAt     DateTime  @default(now())

  ticket Ticket @relation(fields: [ticketId], references: [id], onDelete: Cascade)

  @@index([ticketId])
  @@index([active])
}
```

## 8. API Contract Summary

| Method | Path | Summary | Success Status |
|--------|------|---------|----------------|
| `GET` | `/api/requesters` | List all active development requesters | `200 OK` |
| `GET` | `/api/categories` | List request categories (existing) | `200 OK` |
| `GET` | `/api/related-systems` | List active related systems | `200 OK` |
| `POST` | `/api/tickets` | Create a new ticket (with optional attachments) | `201 Created` |
| `GET` | `/api/tickets` | Query own tickets (search, filter, sort, page) | `200 OK` |
| `GET` | `/api/tickets/:id` | Get single ticket detail (enforces ownership) | `200 OK` |
| `POST` | `/api/tickets/:id/attachments`| Upload attachment to owned ticket | `201 Created` |
| `GET` | `/api/attachments/:id/download`| Download active attachment file | `200 OK` |
| `PATCH`| `/api/attachments/:id/remove` | Soft-remove attachment with reason | `200 OK` |

## 9. Acceptance Criteria (AC)

- **AC-01 (Requester List Filtering):** Given the database has active and inactive requesters, when `GET /api/requesters` is called, then only requesters with `active: true` are returned.
- **AC-02 (Requester Context Selection):** Given no requester is currently chosen, when the user opens the application, then the Development Requester Selector screen is displayed.
- **AC-03 (Header Identity Display):** Given Requester "Jennifer Anderson" is selected, when navigating to any page, then "Jennifer Anderson" is prominently displayed in the header with a "Change Requester" option.
- **AC-04 (Valid Ticket Creation):** Given valid form inputs, when the requester submits the Create Ticket form, then a ticket is persisted with status `New`, an official Ticket Number `TKT-YYYY-XXXXXX` is returned, and a success confirmation view is shown.
- **AC-05 (Client-Side Validation):** Given an empty summary or description under 10 chars, when the user attempts submission, then field-level red validation messages appear and the API is not called.
- **AC-06 (Network/Server Failure Resilience):** Given the backend is unreachable or returns 500 during ticket creation, when submission fails, then a clear error banner appears and all form inputs remain intact.
- **AC-07 (Strict Ticket Ownership Isolation):** Given Requester A created Ticket #101, when Requester B queries `/api/tickets` or navigates to My Tickets, then Ticket #101 is not returned or listed.
- **AC-08 (Direct Ticket Detail Access Protection):** Given Ticket #101 belongs to Requester A, when Requester B attempts `GET /api/tickets/101`, then the server returns HTTP 404 or 403 and the UI shows an unauthorized/not found state.
- **AC-09 (Ticket Search & Filter):** Given multiple owned tickets, when the requester enters a keyword or selects a Category filter, then only matching owned tickets are displayed.
- **AC-10 (Empty & No-Results States):** Given a requester has no tickets, the empty state displays a friendly prompt to "Create your first ticket". When search filters yield no matches, a no-results state with a "Clear Filters" button is shown.
- **AC-11 (Attachment Validation):** Given a file exceeding 5 MB or with an unsupported extension (e.g., `.exe`, `.zip`), when selected, then the file is rejected with a descriptive error message.
- **AC-12 (Active Attachment Limit):** Given a ticket already has 5 active attachments, when attempting to upload a 6th file, then the upload is blocked with an error indicating the 5-attachment maximum.
- **AC-13 (Soft-Removal Execution):** Given an active attachment on an owned ticket, when the requester removes it with a valid reason, then the attachment status becomes inactive, `removedAt` is recorded, and the UI marks it as "Removed".
- **AC-14 (Blocked Download for Removed File):** Given a soft-removed attachment, when a download is attempted via API or UI, then the request returns HTTP 410 Gone or 404 Not Found.
- **AC-15 (Responsive Usability):** Given any supported viewport (Desktop 1200px, Tablet 800px, Mobile 375px), all form controls, tables/cards, badges, and buttons remain accessible without horizontal page scroll or text truncation.

## 11. Assumptions & Decisions
1. **Ticket Number Format:** Backend generates `TKT-` followed by the 4-digit current year and a 6-digit zero-padded incremental sequence (e.g. `TKT-2026-000101`).
2. **Requester State Storage:** Selected requester ID is stored in client `localStorage` so refreshing the browser retains the active test context.
3. **File Storage Strategy:** Attachment binaries are stored in `server/uploads/` on the local file system with uniquely generated UUID filenames; metadata and original filenames are stored in PostgreSQL.
4. **Soft-removal Reason Requirement:** Removal reason must be at least 5 characters to ensure meaningful audit logs.
